PR creation workflow (/finale) MUST follow these rules:

1. **Self-assign**: Always use `-a @me` on `gh pr create` so the PR is assigned to the creating user.

2. **Labels**: Inherit labels from the originating issue AND always add `llm_assisted` for any LLM-involved PR. Use `-l` flags on `gh pr create`.

3. **Milestone**: Inherit milestone from the originating issue. Use `-m` on `gh pr create`.

4. **Projects**: Add to BOTH organization projects at creation time using `-p "Unbound Force Planning" -p "Compliance Automation planning"` on `gh pr create`. This requires `project` scope (`gh auth refresh -h github.com -s project`).

5. **Project status — set to "Ready for Review" immediately after creation** using this efficient 2-command pattern per project:

```bash
# Unbound Force Planning (unbound-force org, project #3)
ITEM_ID=$(gh project item-add 3 --owner unbound-force --url "$PR_URL" --format json --jq '.id')
gh project item-edit --id "$ITEM_ID" --project-id "PVT_kwDOD616js4BaE-9" --field-id "PVTSSF_lADOD616js4BaE-9zhU_Fcc" --single-select-option-id "1b85230a"

# Compliance Automation planning (complytime org, project #14)
ITEM_ID=$(gh project item-add 14 --owner complytime --url "$PR_URL" --format json --jq '.id')
gh project item-edit --id "$ITEM_ID" --project-id "PVT_kwDOCtVpQc4Ber79" --field-id "PVTSSF_lADOCtVpQc4Ber79zhZESGk" --single-select-option-id "61a37675"
```

Note: `gh pr create -p` adds to projects but does NOT set status (defaults to Backlog). The `item-add` + `item-edit` pattern above handles both adding and setting status in one shot, replacing the need for `-p` flags. Choose one approach or the other — using `item-add` is preferred because it returns the item ID needed for status setting.
